Separate the phases

Prefill and decode run the same weights through different shapes.

The phase distinction explains why one average “model latency” cannot predict a serving workload.

Prefill processes a prompt block together

Many queries now
PREFILL
For each layer, compute representations and K/V state for (B\times S_{prompt}) query positions.

Large token dimensions create GEMMs with more reuse and parallel work, while causal attention grows with prompt length.

Clarify that serving systems may chunk a prompt. The conceptual regime remains many new query tokens per request.

Decode advances one position per live sequence

One new query, growing history
DECODE
For each step, compute one new hidden position, append its K/V, and attend over the existing history.

At batch 1, dense projections resemble matrix-vector work; batching turns the token dimension into a larger matrix dimension.

The attended history grows while the number of new queries remains one per sequence.

Dense projections expose the phase through M

Flatten token positions
$$[M,d_{model}]\,[d_{model},d_{out}]\rightarrow[M,d_{out}]$$
prefill(M=B\times S_{chunk})
decode(M=B_{live})
This flattening is a reasoning device. Actual kernels, padding, fused projections, and tensor layouts depend on the implementation.

One weight tile can serve many token rows

Why M matters

Small M

  • little reuse per weight load
  • less parallel work
  • launch and memory latency visible

Large M

  • weights amortized across rows
  • tensor cores better occupied
  • activations and compute also grow
Do not claim batching makes weights free. It changes bytes per useful operation and eventually hits another ceiling.

A transfer-only bound explains batch-1 decode

Hypothetical 600 GB/s device
$$\frac{3.0\times10^9\times2\ \mathrm{B}}{600\times10^9\ \mathrm{B/s}}=0.010\ \mathrm{s}\Rightarrow100\ \mathrm{steps/s}$$

Real throughput is lower or behavior differs because bandwidth is not fully attainable, other tensors move, caches may help, and kernels incur overhead.

The shortcut predicts scale—not a trace

What (2P) omits
Bad conclusion

“The model is 3B, therefore every token costs exactly 6 GFLOP.”

Attention depends on context; embeddings may be tied; MoE activates subsets; kernels add elementwise work; implementations fuse and count operations differently.
Use 2P as a prior. Replace it with measured kernel attribution when decisions depend on the residual terms.

Prefill and decode compete for one device

Different objectives

Long prefill

Efficient large work can occupy the GPU long enough to delay token cadence for already-streaming requests.

Decode steps

Frequent small work protects inter-token latency but can leave compute underfilled.

Chunked prefill is a later scheduling response. Here we establish why the objectives conflict.
