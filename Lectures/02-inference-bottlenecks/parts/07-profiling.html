Profile in layers

User clock first. Timeline second. Kernel counters only when the question demands them.

Profiling is not one tool. Each layer answers a different question and perturbs the workload differently.

Choose the instrument from the question

Four layers of evidence
InstrumentBest questionBlind spot
wall clock / request tracewhat did the user wait for?kernel mechanism
CUDA eventshow long was this device interval?CPU gaps and queueing
system timelinewhere are launches, copies, gaps, overlap?deep kernel counters
kernel profilerwhy is this kernel below a roof?unprofiled end-to-end context
The narrowest instrument is not automatically the most truthful for product latency.

The CPU can stop its timer before the GPU finishes

CUDA is asynchronous
Broken benchmark

“`perf_counter()` measured the kernel.”

Synchronize before and after a CPU timer, or use CUDA events for a device interval. State exactly which interval you measured.
Synchronization is a measurement boundary and can alter overlap; use it deliberately, not throughout production code.

Two correct timers answer different questions

Minimal patterns

Synchronized wall interval

Python
torch.cuda.synchronize()
t0 = time.perf_counter()
y = model(**x)
torch.cuda.synchronize()
wall_s = time.perf_counter() - t0

CUDA event interval

Python
start.record()
y = model(**x)
end.record()
end.synchronize()
gpu_ms = start.elapsed_time(end)
Wall time includes CPU submission between boundaries; event time follows GPU stream timing. Neither includes prior request queue time unless the boundary is placed there.

The hottest kernel may not own the lost time

Production failure story

Misdiagnosis

  • GEMM is 55% of kernel time
  • team makes GEMM 1.10× faster
  • expects 5.5% end-to-end gain

Timeline truth

  • GPU kernels are only 60% of wall time
  • 40% is CPU launch/synchronization gaps
  • Amdahl: 0.33×(1−1/1.10)=3.0% gain
The optimized region owns 0.60×0.55=33% of wall time. Making it 1.10× faster saves 0.33×(1−1/1.10)=3.0% end-to-end, not 5.5%.
