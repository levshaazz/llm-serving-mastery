Build a roofline

Operations per byte determine which hardware ceiling you meet first.

Roofline is an upper-bound model. Its value is making a prediction falsifiable, not reproducing every millisecond.

Arithmetic intensity connects work to traffic

Use one memory boundary
$$I=\frac{\text{operations performed}}{\text{bytes transferred}}\quad[\mathrm{FLOP/B}]$$
numeratorstate the FLOP convention
denominatorHBM, L2, or another declared boundary
Do not divide theoretical FLOPs by tensor allocation size and call it measured intensity. State what traffic is counted.

Two roofs bound attainable performance

Traditional roofline
$$P_{attainable}\le\min(P_{peak},\;BW_{peak}\times I)$$
flat roofpeak compute rate
sloped roofbandwidth × arithmetic intensity
Actual points can lie far below both roofs because of occupancy, dependencies, instruction mix, launch overhead, or nonideal access.

The ridge is where the active ceiling changes

Machine balance
$$I^*=\frac{P_{peak}}{BW_{peak}}$$
I < I*bandwidth roof is lower
I > I*compute roof is lower
A new GPU changes the ridge. A new batch or kernel changes the workload point.

Batch-1 weight work has low first-order intensity

Dense-weight approximation
$$I_{decode,B=1}\approx\frac{2P\ \mathrm{FLOP}}{P\,b_w\ \mathrm{bytes}}=\frac{2}{b_w}\ \mathrm{FLOP/B}$$
BF16(b_w=2\Rightarrow I\approx1) FLOP/B
omitscache hits, KV, activations, attention, fusion
This intentionally crude model explains why streaming weights can dominate. It is not a measured kernel intensity.

Idealized weight reuse moves decode right

Until other traffic matters
$$I_{decode,B}\approx\frac{2PB}{P\,b_w}=\frac{2B}{b_w}\ \mathrm{FLOP/B}$$
B=32, BF16idealized (I\approx32) FLOP/B
not linear foreverKV, activations, compute, shapes, capacity grow
The derivation assumes weights are loaded once for the batch. The profiler determines how much reuse the implementation actually realizes.

Prefill usually offers more reuse—and more work

Do not confuse efficient with cheap

Moves right

  • many token rows reuse weights
  • larger GEMMs fill the machine
  • fusion amortizes launch overhead

Still grows

  • dense work scales with input tokens
  • attention work grows with sequence
  • long kernels can hurt decode cadence
A high-throughput prefill can still have large absolute TTFT for a long prompt.

A memory-bound kernel can keep the GPU “busy”

Activity is not issue efficiency
Dashboard myth

“Memory-bound means low GPU utilization.”

Kernels may be continuously active while arithmetic pipelines wait on data. Use achieved bandwidth, compute throughput, stalls, and roof proximity.
One activity gauge cannot separate compute issue, memory stalls, or small-kernel occupancy.

Far below both roofs is a clue, not a verdict

Look for another ceiling
Bad verdict

“The GPU is poorly designed.”

Small shapes, launch gaps, dependencies, low occupancy, divergence, poor access, throttled clocks, or measurement mismatch can dominate.
A roofline narrows questions; it does not replace a timeline or kernel analysis.
