Why serving
is hard

64 guests walk in at once. What happens to a model that was only ever asked one question at a time?

The hook section: a back-of-the-envelope argument, then a live demo that checks it.
"

the premise of this course
A model that answers one prompt in two seconds on your laptop is a demo. A service that answers two hundred people at once, with a predictable first-token delay, without running out of memory, at a known cost per million tokens — that is what this course builds. The trail is the course in four stones: one stove, a better cooking system (vLLM), more stoves (multi-GPU), more kitchens (Kubernetes).
The naive kitchen

transformers.pipeline behind a web server is this kitchen: every order is cooked perfectly — one at a time.

This is how most first deployments look: wrap pipeline() in FastAPI, put a lock around generate(), ship. It works beautifully for one user. Next slide: what the 64th guest experiences.

Why one order at a time wastes the stove

Every decode step reads all the weights
$$ t_{\text{step}} \;\gtrsim\; \frac{\text{bytes of weights}}{\text{memory bandwidth}} \;=\; \frac{8\ \text{GB}}{896\ \text{GB/s}} \;\approx\; 9\ \text{ms} $$
B = 1
One token per step for one request →
≤ ~110 tokens/s, no matter how fast the math units are.
B = 64
The same weight read serves 64 requests →
ceiling ~64× higher, until compute or memory runs out.
⇒
Batching is cheap in weight traffic during decode.
Compute, KV traffic and scheduling still grow.
Example: a 4B-parameter model in BF16 = 8 GB of weights; the judge GPU (RTX 5070 Ti) has about 896 GB/s of memory bandwidth. To produce one token, the GPU has to stream every weight from memory once: ≈ 9 ms. So a single request is capped near 110 tokens/s — the arithmetic units sit mostly idle, waiting for memory. If 64 requests decode in the same step, the weight traffic can be amortized across the batch. That does not make batching free: matrix compute, KV-cache reads and writes, scheduling work and memory capacity all grow, and the workload eventually becomes compute-bound or runs out of KV cache. This is a lower bound on step time and an upper bound on speed — real numbers are lower. Topic 2 does this properly (roofline, arithmetic intensity).

Common misconception

Bust the myth
What people think

“Our LLM is slow under load. We need a faster GPU.”

Under load, a serial server is limited by scheduling and memory, not by FLOPs. A GPU with twice the memory bandwidth halves the 6.8-minute wait to 3.4 minutes. Serving all 64 orders together — continuous batching, a well-managed KV cache — turns minutes into seconds on the same GPU. That is the whole course in one sentence.
Get the misconception out loud first — ask who would buy the bigger GPU. Then reveal. The rest of the course is the set of software moves that make the same hardware serve an order of magnitude more people.

The arithmetic: 2 (K and V) × 36 layers × 8 KV heads × 128 head dimension × 2 bytes = 147 456 bytes ≈ 144 KiB per token. A representative 4B-class configuration; your model's config.json gives its own L, H_kv and d_h. The KV cache grows with every prompt token and every generated token, for every request that is in flight. Next slide: what that means inside 16 GB.

Every lever buys counter space

Quantized weights and KV cache, PagedAttention's no-waste allocation, prefix caching — topics 3, 5 and 7.

6·10⁹ / 147 456 ≈ 40 700 tokens in total, ≈ 636 per request at 64 concurrent requests — prompt plus answer. That is why the leaderboard rule is stated in tokens: 64 concurrent requests × (512 prompt + 256 answer) ≈ 49k tokens of KV cache next to the weights, in 16 GB. This particular 4B-in-BF16, 8-KV-head example does not fit. That is model-specific, not a proof that quantization is mandatory: a grouped-query model such as Qwen2.5-3B with 2 KV heads needs only about 36 KiB per token in BF16, so roughly 49k tokens consume about 1.7 GiB of KV cache. Topic 3 treats quantization as one trade-off among model architecture, context, batching and runtime overhead. The ~2 GB runtime figure is a rough allowance (CUDA context, activations, CUDA graphs), not a constant.
The fix, in one picture

Continuous batching: one wok, many orders. A new order joins at the next toss; a finished plate leaves at the next toss. Nobody waits for the whole table.

Preview of topics 4–7. Static batching waits until a batch is full and until its longest answer is done. Continuous (iteration-level) batching re-forms the batch at every decode step: requests enter and leave the running batch individually (Orca, OSDI 2022; vLLM). PagedAttention (vLLM, SOSP 2023) is the counter split into small fixed trays, so no guest reserves space they never use. We do not explain them today — we just watch the effect.

set -euo pipefail
exec /runtime/.venv/bin/vllm serve \
  Qwen/Qwen2.5-3B-Instruct \

Fixed: port 8000, model name submission, streaming /v1/chat/completions that honours max_tokens and ignore_eos and takes 4096-token requests. Start from submission-template/ in the course repo.

The contract is strict on purpose: I must be able to literally clone your repository and run it. prepare.sh gets network access before any secret seed or prompts exist; it installs the locked environment and fetches the declared immutable model revision into a fresh per-run cache. The measured serve.sh then starts on an internal Docker network with no egress. A Dockerfile is the alternative, but it must bake in everything needed offline. The model and stack may change between rounds. The reference is Qwen2.5-3B-Instruct on plain vLLM, FP16: a starting point, not a recommendation. Hidden probes check each response separately, so a high average cannot hide early stopping.

What this means for you

Develop and debug on Colab; trust only the judge's numbers. Low-precision tricks (FP8, NVFP4) cannot be tested on a T4 — use the weekly dry-run logs to check that they start on Blackwell.

An optimization that wins on the T4 may not transfer, and vice versa: the judge has ~2.8× the memory bandwidth, and supports data types the T4 does not have at all. That is realistic — production hardware is rarely your laptop. Write down in your journal which results came from Colab and which from the judge.

StepRule

Top to bottom, every round. The snapshot makes the deadline real. A server that does not start, or that got fast by getting dumb, scores zero — quality, latency, errors and layered hidden probes are independent gates. Length is checked per hidden response, not by the GuideLLM mean; same-model similarity uses the worst pair, not the average; diverse prompts must not collapse to one canned output. These are practical anti-gaming checks, not cryptographic proof, so raw artifacts and provenance are retained for audit. Among valid submissions only S matters: the geometric mean of throughput at 32 and 64 clients. The mark is proportional: half the bar = 2.5 of 5. Each round is worth 4% of the course grade (mark × 0.8); ten rounds = 40%.

Policy

Cheating: zero tolerance. No late submissions — a missed round deadline is a 0 for that round. Gaming the benchmark (caching eval answers, special-casing the prompt set, degrading output to win speed) disqualifies the round.

Mise en place — everything in its place before service starts. For us: a pinned environment, a server that starts from a clean checkout, a benchmark you can re-run, a journal you keep. Do it this week, and every round after that is cooking, not firefighting.
