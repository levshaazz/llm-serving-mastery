Why one order at a time wastes the stove

Every decode step reads all the weights
$$ t_{\text{step}} \;\gtrsim\; \frac{\text{bytes of weights}}{\text{memory bandwidth}} \;=\; \frac{8\ \text{GB}}{896\ \text{GB/s}} \;\approx\; 9\ \text{ms} $$
B = 1
One token per step for one request →
≤ ~110 tokens/s, no matter how fast the math units are.
B = 64
The same weight read serves 64 requests →
ceiling ~64× higher, until compute or memory runs out.
⇒
Batching is almost free in decode.
A serial server throws it away.
Example: a 4B-parameter model in BF16 = 8 GB of weights; the judge GPU (RTX 5070 Ti) has about 896 GB/s of memory bandwidth. To produce one token, the GPU has to stream every weight from memory once: ≈ 9 ms. So a single request is capped near 110 tokens/s — the arithmetic units sit mostly idle, waiting for memory. If 64 requests decode in the same step, the weights are read once and used 64 times: the ceiling goes up ~64×, until you become compute-bound or run out of memory for the KV cache (next slides). This is a lower bound on step time and an upper bound on speed — real numbers are lower. Topic 2 does this properly (roofline, arithmetic intensity).
