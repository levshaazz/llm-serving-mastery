Open-loop and closed-loop tests answer different questions

Arrival semantics

Open loop

Arrivals follow an external schedule. Slow responses do not reduce offered load. Models public traffic and overload.

Closed loop

Each virtual user waits for a response before sending again. Slow service self-throttles the generator.

Little's Law is an identity—not a capacity model

What it omits

It can tell you

  • whether means are mutually consistent
  • how residence inflates in-flight population
  • which population definition you used

It cannot tell you

  • the service-time distribution
  • the saturation knee
  • GPU batching efficiency
  • tail latency or transient behavior

The saturation knee is empirical

Capacity envelope
KNEE
The offered-load region where throughput gains flatten while queues, tail latency, or failures accelerate.

Find it by sweeping load under a fixed workload contract; do not infer it from GPU utilization alone.

Service time and response time are different clocks

Queueing decomposition

Service time

Time the system actively needs to progress the request, under a precisely defined scheduling model.

Response time

Queue residence + service + transfers + buffering as observed at the chosen boundary.

High GPU utilization is not the objective

Resource metric ≠ product outcome
Dashboard comfort

“The GPU is at 99%, so the system is efficient.”

The GPU can be busy generating late, cancelled, retried, or low-priority tokens. Pair utilization with goodput, queue age, cancellation lag, and SLO attainment.

A slow system can make a closed-loop test send less load

Coordinated omission

What happens

The generator waits for slow responses and omits requests that would have arrived on the intended schedule.

Consequence

The reported latency distribution excludes the waiting those missing requests would have experienced.
