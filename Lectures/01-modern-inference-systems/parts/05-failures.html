A retry is a budgeted policy decision

Not an exception handler

Retry only when

  • the operation is safe/idempotent
  • the remaining deadline is useful
  • the failure is plausibly transient
  • a shared retry budget permits it

Shape the retry

  • bounded attempts
  • exponential backoff + jitter
  • server hints where available
  • deduplication or idempotency key

Propagate a deadline, not a fresh timeout

End-to-end budget

Fresh timeout per hop

Each service gets 5 s, so a chain can exceed the user's 5 s by multiples and continue stale work.

Absolute deadline

Every stage sees the remaining budget and can reject work that cannot finish usefully.
