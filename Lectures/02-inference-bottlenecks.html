Separate the phases

Prefill and decode run the same weights through different shapes.

The phase distinction explains why one average “model latency” cannot predict a serving workload.

Prefill processes a prompt block together

Many queries now
PREFILL
For each layer, compute representations and K/V state for (B\times S_{prompt}) query positions.

Large token dimensions create GEMMs with more reuse and parallel work, while causal attention grows with prompt length.

Clarify that serving systems may chunk a prompt. The conceptual regime remains many new query tokens per request.

Decode advances one position per live sequence

One new query, growing history
DECODE
For each step, compute one new hidden position, append its K/V, and attend over the existing history.

At batch 1, dense projections resemble matrix-vector work; batching turns the token dimension into a larger matrix dimension.

The attended history grows while the number of new queries remains one per sequence.

Dense projections expose the phase through M

Flatten token positions

prefill(M=B\times S_{chunk})
decode(M=B_{live})
This flattening is a reasoning device. Actual kernels, padding, fused projections, and tensor layouts depend on the implementation.

Small M

Large M

Tensor role predicts desired placement

But software does not control every hit

Long-lived

  • weights: device memory, reused by kernels
  • KV cache: device memory, grows per request
  • allocator pools: reserved for reuse

Short-lived / tiled

  • activations and workspace
  • L2-resident reused lines when lucky
  • shared-memory tiles and registers
“Stored in HBM” does not mean every access necessarily reaches HBM; caches mediate actual traffic.

Reuse is the bridge from bytes to operations

The performance lever
DATA REUSE
Perform more useful operations before the same data must be fetched again from a slower memory level.

Batching reuses weights across token rows; tiling reuses blocks on chip; fusion keeps intermediate values closer to compute.

Reuse does not reduce model semantics. It reorganizes execution and data movement.

Equal bytes can produce unequal transactions

Access pattern matters

Friendly access

Neighboring threads access neighboring addresses; transactions are coalesced and useful payload is high.

Hostile access

Scattered or misaligned accesses request extra memory transactions and waste transferred bytes.

The lesson is not to hand-optimize CUDA today; it is to know why nominal tensor size alone does not equal observed traffic.

Fusion removes materialization boundaries

Same math, fewer round trips
$$Y=f_3(f_2(f_1(X)))\quad\text{without writing every intermediate to HBM}$$
saveslaunches and intermediate reads/writes
does not savethe required mathematical dependency
Fusion may increase register pressure or reduce flexibility. It is a trade-off, not a universal free win.

FlashAttention is an IO algorithm

Exact attention, tiled differently

Naïve mental model

Materialize the (S\times S) score matrix in device memory, then read it again for softmax and value aggregation.

IO-aware model

Tile Q/K/V and maintain online softmax statistics so less intermediate state travels to HBM.

Cite Dao et al.: the result is exact attention. Avoid claiming it changes the quadratic arithmetic of dense attention.

Less attention IO does not erase generation physics

Scope the optimization
Overclaim

“FlashAttention solves long-context inference.”

Autoregressive steps remain serial; KV state still grows; decode still reads history; weights, MLPs, capacity, and scheduling remain.
Optimization claims need a denominator: which phase, which kernel, which context, and which end-to-end metric?

Build a roofline

Operations per byte determine which hardware ceiling you meet first.

Roofline is an upper-bound model. Its value is making a prediction falsifiable, not reproducing every millisecond.

Arithmetic intensity connects work to traffic

Use one memory boundary
$$I=\frac{\text{operations performed}}{\text{bytes transferred}}\quad[\mathrm{FLOP/B}]$$
numeratorstate the FLOP convention
denominatorHBM, L2, or another declared boundary
Do not divide theoretical FLOPs by tensor allocation size and call it measured intensity. State what traffic is counted.

Two roofs bound attainable performance

Traditional roofline
$$P_{attainable}\le\min(P_{peak},\;BW_{peak}\times I)$$

The ridge is where the active ceiling changes

Machine balance
$$I^*=\frac{P_{peak}}{BW_{peak}}$$
I < I*bandwidth roof is lower
I > I*compute roof is lower

Budget the KV cache

Saved recomputation becomes growing per-request state.

KV caching is a time–space trade: retain projections of history so each decode step does not recompute them.

Without a cache, history is repeatedly projected

Correct but wasteful decode

At step t

Run the entire prefix (x_{1:t}) again to reconstruct every layer's keys and values.

Across T steps

The model's hidden state at a position is layer-specific; we cache K and V for every layer, not one global token vector.

The CPU can stop its timer before the GPU finishes

CUDA is asynchronous
Broken benchmark

“`perf_counter()` measured the kernel.”

Synchronize before and after a CPU timer, or use CUDA events for a device interval. State exactly which interval you measured.
Synchronization is a measurement boundary and can alter overlap; use it deliberately, not throughout production code.

The hottest kernel may not own the lost time

Production failure story

Misdiagnosis

  • GEMM is 55% of kernel time
  • team optimizes GEMM by 10%
  • expects 5.5% end-to-end gain

Timeline truth

  • GPU kernels are only 60% of wall time
  • 40% is CPU launch/synchronization gaps
  • affected wall-time share is 0.60×0.55=0.33
A 10% speedup of a region owning 33% of wall time yields about 3.3% end-to-end for a small-change approximation, not 5.5%.
