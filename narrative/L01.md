# L01 — Modern LLM inference systems & production challenges

## Production question

An endpoint produces the right answer for one prompt. What additional system must exist before we can
promise useful, fast, and reliable answers to many users—and how do we know the promise holds?

## Starting model → target model

- Start: “inference server = model + HTTP”.
- Finish: “serving system = admission + scheduling + model execution + streaming + cancellation +
  observability + lifecycle management, governed by an explicit workload/SLO/measurement contract”.

## Narrative beats (92 slides)

1. **Hook — the 09:00 incident (1–8).** One request works; 64 clients create queues, retries, and stale
   work. Establish the four questions: boundary, time, load, failure.
2. **System boundary (9–22).** Follow one request through client, edge, gateway, admission, scheduler,
   worker, tokenizer, model runner, sampler, streamer, metrics. Separate data/control/observability planes.
   Interactive architecture reveal.
3. **Time has phases (23–38).** Arrival → queue → prefill → first token → decode → final byte. Define
   TTFT, ITL/TPOT, E2E, goodput. Worked trace: 512 input, 128 output, p99 promise. Interactive sequence
   with a running latency budget.
4. **Load changes the answer (39–55).** Open vs closed loop, concurrency vs rate, Little's Law, service
   time vs response time, saturation knee. Worked examples: 8 req/s × 0.5 s; coordinated omission;
   percentile aggregation. Queue model is explicitly illustrative, not a GPU model.
5. **The production failure loops (56–69).** Backpressure, bounded queues, deadlines, cancellation,
   retry amplification, fan-out tails, cold starts, deploy/rollback. Interactive overload walkthrough.
6. **Architectures are choices (70–81).** Offline pipeline, single engine, split gateway/worker,
   disaggregated overview, multi-tenant routing, stateful prefix/KV concerns, autoscaling signals.
   Compare three real workload archetypes without prescribing one universal design.
7. **Measure before optimizing (82–89).** Reproducible experiment contract, concrete API payload/stream,
   trace and metric schema, benchmark traps, notebook protocol, diagnosis worksheet.
8. **Payoff (90–92).** Decision checklist, sourced reading, exit ticket and bridge to Topic 2.

## Worked examples

1. Trace arithmetic: gateway 8 ms + queue 220 ms + prefill 90 ms + transfer 5 ms gives TTFT 323 ms;
   127 decode gaps × 22 ms gives 2.794 s; E2E ≈ 3.117 s.
2. Goodput: 120 completed requests/min, 110 correct, 90 inside both SLOs → throughput 2.0 req/s,
   successful throughput 1.83 req/s, goodput 1.50 req/s.
3. Little's Law: 8 req/s × 0.5 s = 4 in flight; changing residence to 2 s at the same arrival rate
   implies 16 in flight, not more capacity.
4. Retry amplification: 100 originals, 20% time out, each timed-out request retries once → 120 attempts;
   if retries also time out at 20%, the next wave adds 4 more. Attempts are load, not users.
5. Fan-out tail: if one shard meets its deadline with probability 0.99, all 20 independent shards do so
   with probability 0.99^20 ≈ 0.818. Independence is an explicit simplifying assumption.

## Production scenarios

- Chat assistant: bursty open-loop arrivals, long variable outputs, user cancellation, TTFT-sensitive.
- Batch summarization: controlled backlog, throughput/cost-sensitive, relaxed inter-token latency.
- Coding copilot: short deadline, cancellation on keystroke, stale work is actively harmful.
- Fan-out agent: multiple downstream calls multiply tail and failure probability.

## Scope boundary

This lecture names prefill/decode, batching, KV state, and parallel/disaggregated architectures only as
system concepts. Topic 2 derives compute/memory bottlenecks; later topics implement vLLM, quantization,
multi-GPU, Kubernetes, and autoscaling in depth.
