# L02 — Inference bottlenecks: KV cache, memory hierarchy, autoregression

## Production question

The GPU reports high utilization, yet one workload is slow, another runs out of memory, and a larger
batch suddenly becomes much faster. Which resource is actually limiting each phase, and what evidence
would distinguish compute, memory bandwidth, capacity, launch overhead, and queueing?

## Starting model → target model

- Start: “a faster GPU or more GPU utilization means faster inference”.
- Finish: “prefill and decode are different workloads; predict their ceilings from operations, bytes,
  shapes, and live state, then use a profiler and controlled experiments to falsify that prediction”.

## Scope boundary

This lecture derives the dense decoder forward path, arithmetic intensity, memory hierarchy, and KV-cache
capacity. It uses batching only to expose changing matrix shapes. Topic 3 owns weight/KV quantization;
Topic 4 owns the vLLM engine; Topic 5 owns PagedAttention and continuous batching. The lecture may name
those techniques as hypotheses, but must not teach their implementation early.

## Worked examples and checked arithmetic

1. **Serial decode time.** A 128-token answer has 128 dependent forward/sampling steps. If median
   inter-token latency is 22 ms after the first token, the 127 following gaps contribute
   `127 × 0.022 = 2.794 s`; batching can share device work but cannot remove this dependency chain.
2. **Weight-stream lower bound.** For an explicitly approximate 3.0B-parameter dense model in BF16,
   weights occupy `3.0e9 × 2 = 6.0e9 bytes`. If a batch-1 decode step streamed them once from a
   hypothetical 600 GB/s memory system, the transfer-only lower bound is `6/600 = 0.010 s`, or at most
   100 steps/s. This ignores cache, other tensors, kernels, and attainable bandwidth.
3. **Roofline ridge.** A hypothetical device with 60 TFLOP/s peak and 600 GB/s peak has a ridge at
   `60e12 / 600e9 = 100 FLOP/byte`. A kernel at 20 FLOP/byte has a bandwidth roof of 12 TFLOP/s.
4. **Qwen2.5-3B KV cache.** Published config values: 36 layers, 2 KV heads, head dimension
   `2048/16 = 128`. BF16 cache: `2 × 36 × 2 × 128 × 2 = 36,864 bytes = 36 KiB/token`.
   `64 × (512+256) = 49,152` live tokens require exactly `1,811,939,328 bytes ≈ 1.688 GiB`, excluding
   allocator metadata and other runtime memory.
5. **MHA counterfactual.** Holding all else fixed but using 16 KV heads gives `288 KiB/token`; 49,152
   tokens require `13.5 GiB`. This isolates the cache effect of KV-head sharing; it is not a claim that
   the resulting models are otherwise equivalent.
6. **Effective bandwidth.** Reading and writing a 4096×4096 FP16 tensor transfers
   `4096² × 2 bytes × 2 = 67,108,864 bytes`. At 0.2 ms, effective bandwidth is
   `67,108,864 / 0.0002 / 1e9 ≈ 335.5 GB/s` using decimal GB.

## Production scenarios

- **Prompt-heavy document analysis:** prefill dominates TTFT; long prompts stress attention work and transient
  activation traffic, while short answers limit decode residence.
- **Long-form generation:** decode dominates residence time; KV capacity and per-step KV reads grow with context.
- **Mixed tenant incident:** long prefills interfere with decode cadence; high aggregate GPU utilization hides
  the phase-specific SLO failure.
- **Token-blind admission:** request-count limit admits equal numbers of radically unequal sequences and OOMs.
